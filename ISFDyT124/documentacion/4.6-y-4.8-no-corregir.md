# Por qué 4.6 y 4.8 no se van a corregir

Estos dos hallazgos de testing quedaron registrados en el EDT/Cronograma (items
4.6 y 4.8), pero al revisar cómo está armado el proyecto se determinó que la
corrección propuesta rompe cosas que están hechas a propósito. Por eso se
sacaron de los tickets de collabkit y quedan documentados acá para que quede
el porqué, en vez de perderse.

## 4.6 — "Permite materias duplicadas"

**Lo que reportó testing:** el alta de una Materia no valida que ya exista
otra con la misma denominación (ej. se puede crear "Matemática" dos veces).

**Por qué no es un bug:** `Materia` no es una entidad que pertenezca a una
sola Carrera. La relación entre ambas está modelada como muchos a muchos, a
través de la tabla intermedia `CarreraMateria`
(`ISFDyT124/Models/CarreraMateria.cs`):

```csharp
public int CaId { get; set; }   // FK a Carrera
public int MaId { get; set; }   // FK a Materia
```

Y `MateriasController.Create` (POST) lo confirma en código: primero crea la
`Materia`, y **después, si se eligió una carrera, crea aparte la fila en
`CarreraMateria`** que la vincula:

```csharp
_context.Add(materia);
await _context.SaveChangesAsync();
if (CaId.HasValue)
{
    var rel = new CarreraMateria { CaId = CaId.Value, MaId = materia.MaId };
    _context.CarreraMaterias.Add(rel);
    await _context.SaveChangesAsync();
}
```

Este diseño existe para que una misma materia (ej. "Inglés", "Matemática",
"Informática") se pueda dictar en más de una carrera sin duplicar el
registro — se crea una vez la `Materia` y se la vincula a todas las carreras
que correspondan mediante `CarreraMateria`. Es exactamente el mismo patrón
que ya usa el ticket 4.3 ("Múltiples materias/carreras por docente"), que da
por sentado que esa relación muchos a muchos es intencional y hay que
explotarla, no restringirla.

Si se agrega una validación de `MaDenominacion` única a nivel global (como
proponía el hallazgo), pasa a ser imposible tener "Matemática" en dos carreras
distintas — se rompe el caso de uso real que la tabla `CarreraMateria` fue
diseñada para resolver.

**Qué sí podría tener sentido (no se hizo, queda anotado por si sirve a
futuro):** evitar que la *misma* Carrera tenga la *misma* Materia vinculada
dos veces (un duplicado dentro de `CarreraMateria`, no en `Materia`). Eso es
un problema distinto al que reportó testing y no estaba pedido — se menciona
solo para no confundirlo con "prohibir nombres repetidos", que sí rompe el
diseño.

## 4.8 — "Paso redundante Detalles → Editar"

**Lo que reportó testing:** para editar una Materia hay que entrar primero a
"Detalles" y desde ahí ir a "Editar" — un clic de más, se sugería que el link
de la fila lleve directo a Editar.

**Por qué no se va a hacer así:** el proyecto mantiene, de forma consistente
en las tres pantallas ABM que existen (Materias, Carreras, y Alumnos desde el
ticket 3.3), una separación deliberada entre una vista de **Details**
(solo lectura) y una vista de **Edit** (formulario). Se puede confirmar en
los controllers y en las carpetas de vistas:

- `MateriasController` tiene acciones `Details(int? MaId)` y
  `Edit(int? MaId)` separadas, cada una con su propio `.cshtml`
  (`Views/Materias/Details.cshtml` y `Views/Materias/Edit.cshtml`).
- `CarrerasController` repite exactamente el mismo patrón
  (`Views/Carreras/Details.cshtml` / `Views/Carreras/Edit.cshtml`).
- El módulo de Alumnos (ticket 3.3, ya en "Hecho") se hizo siguiendo esa
  misma convención.

Colapsar Details en Edit para Materias (que el link de la fila lleve directo
a editar y desaparezca la vista de solo lectura) rompería esa consistencia:
Materias quedaría con un comportamiento distinto al de Carreras y Alumnos sin
que haya un motivo funcional que lo justifique — solo achica un clic para un
caso de uso (editar) a costa de sacar la posibilidad de mirar los datos sin
riesgo de tocarlos por error, que es justamente para lo que existe la vista
de Details en las otras dos pantallas.

**Qué sí podría tener sentido (no se hizo, queda anotado por si sirve a
futuro):** agregar el botón "Editar" *también* como acceso directo desde la
fila del listado (`Index`), sin sacar la vista de Details. Así se gana el
atajo que pedía testing sin romper la consistencia entre pantallas. No se
implementó porque no era lo que pedía el hallazgo original ni se armó ticket
para eso — se dejó anotado acá para que quede como opción futura si el equipo
lo quiere retomar.
